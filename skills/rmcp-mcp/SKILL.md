# RMCP — Rust Model Context Protocol SDK

> **Layer 3: Domain Constraints** (Protocol Implementation)
>
> **Crate:** [`rmcp`](https://crates.io/crates/rmcp) (official Rust MCP SDK)
>
> **Source:** [modelcontextprotocol/rust-sdk](https://github.com/modelcontextprotocol/rust-sdk)

## Core Question

**Am I building an MCP server (exposing tools/resources/prompts) or a client (consuming them)?**

Before writing code:
- Am I exposing **tools** for AI assistants to call?
- Am I exposing **resources** (files, data) for clients to read?
- Am I exposing **prompts** (message templates)?
- Am I building a **client** that connects to MCP servers?
- Which **transport** do I need? (stdio, HTTP, custom)

### Feature Flags Reference

| Feature | Description | Default |
|---------|-------------|---------|
| `server` | Server functionality and tool system | ✅ |
| `client` | Client functionality | |
| `macros` | `#[tool]` / `#[prompt]` macros | ✅ |
| `schemars` | JSON Schema generation for tool definitions | |
| `auth` | OAuth 2.0 authentication support | |
| `elicitation` | Elicitation support | |

### Transport Features

| Feature | Description |
|---------|-------------|
| `transport-io` | Server-side stdio transport |
| `transport-child-process` | Client-side stdio transport (spawns child process) |
| `transport-async-rw` | Generic async read/write transport |
| `transport-streamable-http-client` | Streamable HTTP client (transport-agnostic) |
| `transport-streamable-http-client-reqwest` | Streamable HTTP client with `reqwest` backend |
| `transport-streamable-http-server` | Streamable HTTP server transport |

### TLS Backend Options (HTTP transports)

| Feature | Description |
|---------|-------------|
| `reqwest` | Uses rustls — pure Rust TLS (recommended) |
| `reqwest-native-tls` | Uses platform-native TLS |
| `reqwest-tls-no-provider` | Uses rustls without default crypto provider |

## Architecture Overview

```
┌──────────────────────────────────────────────────┐
│                  Service Layer                    │
│                                                  │
│  ┌──────────────┐        ┌──────────────────┐    │
│  │ ServerHandler │        │  ClientHandler   │    │
│  │  (your impl) │        │   (your impl)    │    │
│  └──────┬───────┘        └────────┬─────────┘    │
│         │                         │              │
│  ┌──────▼─────────────────────────▼──────────┐   │
│  │        ServiceExt::serve(transport)        │   │
│  └──────────────────┬────────────────────────┘   │
│                     │                            │
│  ┌──────────────────▼────────────────────────┐   │
│  │            Transport Layer                 │   │
│  │  stdio | Streamable HTTP | Custom          │   │
│  └────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────┘
```

The key abstraction: **your struct implements `ServerHandler` or `ClientHandler`**, you pick a transport, and call `.serve(transport)` to wire everything together.

## Building a Server

### Minimal Stdio Server with Tools

This is the most common pattern — a server that exposes tools via stdio:

```rust
use rmcp::{
    ServerHandler, ServiceExt,
    handler::server::router::tool::ToolRouter,
    handler::server::wrapper::Parameters,
    model::*,
    schemars::{self, JsonSchema},
    service::RequestContext,
    tool, tool_handler, tool_router,
    transport::stdio,
    ErrorData as McpError, RoleServer,
};
use serde::Deserialize;
use tokio::io::{stdin, stdout};

#[derive(Debug, Deserialize, JsonSchema)]
struct GreetArgs {
    /// Name of the person to greet
    name: String,
}

#[derive(Clone)]
struct MyServer {
    tool_router: ToolRouter<Self>,
}

#[tool_router]
impl MyServer {
    fn new() -> Self {
        Self {
            // Self::tool_router() is auto-generated by #[tool_router]
            tool_router: Self::tool_router(),
        }
    }

    #[tool(description = "Say hello to someone")]
    async fn greet(
        &self,
        Parameters(args): Parameters<GreetArgs>,
    ) -> Result<CallToolResult, McpError> {
        Ok(CallToolResult::success(vec![Content::text(
            format!("Hello, {}!", args.name),
        )]))
    }

    #[tool(description = "Get the current time")]
    fn current_time(&self) -> Result<CallToolResult, McpError> {
        let now = chrono::Utc::now();
        Ok(CallToolResult::success(vec![Content::text(
            now.to_rfc3339(),
        )]))
    }
}

// #[tool_handler] auto-generates call_tool() and list_tools()
#[tool_handler]
impl ServerHandler for MyServer {
    fn get_info(&self) -> ServerInfo {
        ServerInfo::new(
            ServerCapabilities::builder()
                .enable_tools()
                .build(),
        )
        .with_server_info(Implementation::from_build_env())
    }
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let service = MyServer::new();
    let server = service.serve(stdio()).await?;
    // Block until the client disconnects
    server.waiting().await?;
    Ok(())
}
```

### Key Patterns

#### Tool Arguments

Tool arguments are defined as structs deriving `Deserialize` + `JsonSchema`.
Extract with `Parameters<T>`:

```rust
#[derive(Debug, Deserialize, JsonSchema)]
struct CalcArgs {
    /// First operand
    a: f64,
    /// Second operand
    b: f64,
}

#[tool(description = "Add two numbers")]
fn add(
    &self,
    Parameters(CalcArgs { a, b }): Parameters<CalcArgs>,
) -> Result<CallToolResult, McpError> {
    Ok(CallToolResult::success(vec![Content::text(
        (a + b).to_string(),
    )]))
}
```

#### Accessing Request Context

Use `RequestContext<RoleServer>` to access the peer (client) and extensions:

```rust
#[tool(description = "Tool that needs context")]
async fn contextual_tool(
    &self,
    ctx: RequestContext<RoleServer>,
) -> Result<CallToolResult, McpError> {
    // Request something from the client
    let roots = ctx.peer.list_roots().await?;
    Ok(CallToolResult::success(vec![Content::text(
        format!("Client has {} roots", roots.roots.len()),
    )]))
}
```

#### Tool Return Types

Tools can return several types:

| Return Type | Usage |
|-------------|-------|
| `Result<CallToolResult, McpError>` | Most common — explicit success/error |
| `String` | Auto-wrapped in `CallToolResult::success` |
| `CallToolResult` | Direct result without error handling |

## Building a Client

### Stdio Client (spawns a child process)

```rust
use rmcp::{
    ServiceExt,
    model::{CallToolRequestParams, ReadResourceRequestParams},
    object,
    transport::{ConfigureCommandExt, TokioChildProcess},
};
use tokio::process::Command;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    // Connect to a server by spawning it as a child process
    let client = ().serve(
        TokioChildProcess::new(
            Command::new("npx").configure(|cmd| {
                cmd.arg("-y").arg("@modelcontextprotocol/server-everything");
            }),
        )?
    ).await?;

    let server_info = client.peer_info();
    println!("Connected to: {server_info:#?}");

    // List tools
    let tools = client.list_all_tools().await?;

    // Call a tool
    let result = client.call_tool(
        CallToolRequestParams::new("echo")
            .with_arguments(object!({ "message": "hello" })),
    ).await?;

    // List resources
    let resources = client.list_all_resources().await?;

    // Read a resource
    let resource = client.read_resource(
        ReadResourceRequestParams::new("test://static/resource/1"),
    ).await?;

    // Disconnect
    client.cancel().await?;

    Ok(())
}
```

### Streamable HTTP Client

```rust
use rmcp::{
    ServiceExt,
    transport::StreamableHttpClientTransport,
};

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let transport = StreamableHttpClientTransport::builder(
        "http://localhost:8080/mcp".parse()?,
    ).build();

    let client = ().serve(transport).await?;
    // Use client the same way as stdio...
    Ok(())
}
```

## Server Capabilities

### Resources

Expose data (files, database records, API responses) that clients can read:

```rust
use rmcp::{
    ErrorData as McpError, RoleServer, ServerHandler, ServiceExt,
    model::*, service::RequestContext,
};
use serde_json::json;

#[derive(Clone)]
struct MyServer;

impl ServerHandler for MyServer {
    fn get_info(&self) -> ServerInfo {
        ServerInfo {
            capabilities: ServerCapabilities::builder()
                .enable_resources()
                .build(),
            ..Default::default()
        }
    }

    async fn list_resources(
        &self,
        _request: Option<PaginatedRequestParams>,
        _context: RequestContext<RoleServer>,
    ) -> Result<ListResourcesResult, McpError> {
        Ok(ListResourcesResult {
            resources: vec![
                RawResource::new("file:///config.json", "config").no_annotation(),
                RawResource::new("memo://insights", "insights").no_annotation(),
            ],
            next_cursor: None,
            meta: None,
        })
    }

    async fn read_resource(
        &self,
        request: ReadResourceRequestParams,
        _context: RequestContext<RoleServer>,
    ) -> Result<ReadResourceResult, McpError> {
        match request.uri.as_str() {
            "file:///config.json" => Ok(ReadResourceResult {
                contents: vec![ResourceContents::text(
                    r#"{"key": "value"}"#,
                    &request.uri,
                )],
            }),
            _ => Err(McpError::resource_not_found(
                "resource_not_found",
                Some(json!({ "uri": request.uri })),
            )),
        }
    }
}
```

### Prompts

Expose reusable message templates with typed arguments:

```rust
use rmcp::{
    ErrorData as McpError, RoleServer, ServerHandler, ServiceExt,
    handler::server::{router::prompt::PromptRouter, wrapper::Parameters},
    model::*,
    prompt, prompt_handler, prompt_router,
    schemars::JsonSchema,
    service::RequestContext,
};
use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize, JsonSchema)]
pub struct CodeReviewArgs {
    #[schemars(description = "Programming language of the code")]
    pub language: String,
    #[schemars(description = "Focus areas for the review")]
    pub focus_areas: Option<Vec<String>>,
}

#[derive(Clone)]
pub struct MyServer {
    prompt_router: PromptRouter<Self>,
}

#[prompt_router]
impl MyServer {
    fn new() -> Self {
        Self { prompt_router: Self::prompt_router() }
    }

    /// Simple prompt without parameters
    #[prompt(name = "greeting", description = "A simple greeting")]
    async fn greeting(&self) -> Vec<PromptMessage> {
        vec![PromptMessage::new_text(
            PromptMessageRole::User,
            "Hello! How can you help me today?",
        )]
    }

    /// Prompt with typed arguments
    #[prompt(name = "code_review", description = "Review code in a given language")]
    async fn code_review(
        &self,
        Parameters(args): Parameters<CodeReviewArgs>,
    ) -> Result<GetPromptResult, McpError> {
        let focus = args.focus_areas
            .unwrap_or_else(|| vec!["correctness".into()]);
        Ok(GetPromptResult {
            description: Some(format!("Code review for {}", args.language)),
            messages: vec![
                PromptMessage::new_text(
                    PromptMessageRole::User,
                    format!(
                        "Review my {} code. Focus on: {}",
                        args.language, focus.join(", ")
                    ),
                ),
            ],
        })
    }
}

#[prompt_handler]
impl ServerHandler for MyServer {
    fn get_info(&self) -> ServerInfo {
        ServerInfo {
            capabilities: ServerCapabilities::builder()
                .enable_prompts()
                .build(),
            ..Default::default()
        }
    }
}
```

Prompt functions support these return types:
- `Vec<PromptMessage>` — simple message list
- `GetPromptResult` — messages with optional description
- `Result<T, McpError>` — either of the above, with error handling

### Combining Tools + Prompts + Resources

Use both `#[tool_handler]` and `#[prompt_handler]` on the same `ServerHandler` impl,
and enable all capabilities:

```rust
#[derive(Clone)]
struct FullServer {
    tool_router: ToolRouter<Self>,
    prompt_router: PromptRouter<Self>,
}

#[tool_router]
impl FullServer {
    fn new() -> Self {
        Self {
            tool_router: Self::tool_router(),
            prompt_router: Self::prompt_router(),
        }
    }

    #[tool(description = "My tool")]
    async fn my_tool(&self) -> Result<CallToolResult, McpError> {
        Ok(CallToolResult::success(vec![Content::text("result")]))
    }
}

#[prompt_router]
impl FullServer {
    #[prompt(name = "my_prompt", description = "My prompt")]
    async fn my_prompt(&self) -> Vec<PromptMessage> {
        vec![PromptMessage::new_text(PromptMessageRole::User, "Hello")]
    }
}

// Both macros work together
#[prompt_handler]
#[tool_handler]
impl ServerHandler for FullServer {
    fn get_info(&self) -> ServerInfo {
        ServerInfo::new(
            ServerCapabilities::builder()
                .enable_tools()
                .enable_prompts()
                .enable_resources()
                .build(),
        )
    }

    // Implement resource methods manually...
    async fn list_resources(
        &self,
        _request: Option<PaginatedRequestParams>,
        _: RequestContext<RoleServer>,
    ) -> Result<ListResourcesResult, McpError> {
        Ok(ListResourcesResult {
            resources: vec![],
            next_cursor: None,
            meta: None,
        })
    }
}
```

## Notifications

### Progress Notifications (Server → Client)

```rust
// Inside a tool handler:
for i in 0..total_items {
    process_item(i).await;
    context.peer.notify_progress(ProgressNotificationParam {
        progress_token: ProgressToken(NumberOrString::Number(i as i64)),
        progress: i as f64,
        total: Some(total_items as f64),
        message: Some(format!("Processing item {}/{}", i + 1, total_items)),
    }).await?;
}
```

### Cancellation

```rust
// Send a cancellation
context.peer.notify_cancelled(CancelledNotificationParam {
    request_id: the_request_id,
    reason: Some("User requested cancellation".into()),
}).await?;

// Handle cancellation
impl ServerHandler for MyServer {
    async fn on_cancelled(
        &self,
        params: CancelledNotificationParam,
        _context: NotificationContext<RoleServer>,
    ) {
        // Abort work for params.request_id
    }
}
```

### List-Changed Notifications

```rust
// Notify when tools/prompts/resources change
context.peer.notify_tool_list_changed().await?;
context.peer.notify_prompt_list_changed().await?;
context.peer.notify_resource_list_changed().await?;
```

```rust
// Server-side: request a completion from the client
let response = context.peer.create_message(CreateMessageRequestParams {
    meta: None,
    task: None,
    messages: vec![SamplingMessage::user_text("Explain this error")],
    model_preferences: Some(ModelPreferences {
        hints: Some(vec![ModelHint { name: Some("claude".into()) }]),
        cost_priority: Some(0.3),
        speed_priority: Some(0.8),
        intelligence_priority: Some(0.7),
    }),
    system_prompt: Some("You are a helpful assistant.".into()),
    include_context: Some(ContextInclusion::None),
    temperature: Some(0.7),
    max_tokens: 150,
    stop_sequences: None,
    metadata: None,
    tools: None,
    tool_choice: None,
}).await?;

// Client-side: handle sampling requests
impl ClientHandler for MyClient {
    async fn create_message(
        &self,
        params: CreateMessageRequestParams,
        _context: RequestContext<RoleClient>,
    ) -> Result<CreateMessageResult, ErrorData> {
        let response_text = call_your_llm(&params.messages).await;
        Ok(CreateMessageResult {
            message: SamplingMessage::assistant_text(response_text),
            model: "my-model".into(),
            stop_reason: Some(CreateMessageResult::STOP_REASON_END_TURN.into()),
        })
    }
}
```

## Subscriptions

```rust
// Server: enable subscriptions
fn get_info(&self) -> ServerInfo {
    ServerInfo {
        capabilities: ServerCapabilities::builder()
            .enable_resources()
            .enable_resources_subscribe()
            .build(),
        ..Default::default()
    }
}

// Handle subscribe/unsubscribe
async fn subscribe(
    &self,
    request: SubscribeRequestParams,
    _context: RequestContext<RoleServer>,
) -> Result<(), McpError> {
    self.subscriptions.lock().await.insert(request.uri);
    Ok(())
}

// Client: subscribe to resource updates
client.subscribe(SubscribeRequestParams {
    meta: None,
    uri: "file:///config.json".into(),
}).await?;
```

## Transports Reference

| | Client | Server |
|:-:|:-:|:-:|
| **stdio** | `TokioChildProcess` | `stdio()` (from `transport::stdio`) |
| **Streamable HTTP** | `StreamableHttpClientTransport` | `StreamableHttpService` |

Any type implementing the `Transport` trait can be used. `IntoTransport` provides automatic conversions from:
1. `(Sink, Stream)` or combined `Sink + Stream`
2. `(AsyncRead, AsyncWrite)` or combined `AsyncRead + AsyncWrite`
3. A `Worker` implementation
4. A `Transport` implementation directly

## Proc Macro Reference

| Macro | Description |
|-------|-------------|
| `#[tool]` | Mark a function as an MCP tool handler |
| `#[tool_router]` | Generate a tool router from an impl block |

## Decision Flowchart

```
What am I building?
├─ MCP Server (expose tools/resources/prompts to AI)
│   ├─ Transport?
│   │   ├─ Stdio → feature = "transport-io", use stdio()
│   │   ├─ HTTP → feature = "transport-streamable-http-server"
│   │   └─ Custom → implement Transport trait
│   ├─ Tools → #[tool_router] + #[tool] + #[tool_handler]
│   ├─ Resources → impl list_resources() + read_resource() manually
│   ├─ Prompts → #[prompt_router] + #[prompt] + #[prompt_handler]
│   └─ Combine → stack #[prompt_handler] #[tool_handler] on ServerHandler
│
└─ MCP Client (connect to servers)
    ├─ Spawn process → feature = "transport-child-process", TokioChildProcess
    ├─ Connect HTTP → feature = "transport-streamable-http-client-reqwest"
    └─ Call methods → client.list_all_tools(), client.call_tool(), etc.
```

## Anti-Patterns

| Anti-Pattern | Why Bad | Better |
|--------------|---------|--------|
| Manual `call_tool` dispatch | Verbose, error-prone | Use `#[tool_router]` + `#[tool_handler]` macros |
| Blocking in tool handlers | Blocks the tokio runtime | Use `tokio::spawn` or `spawn_blocking` |
| Ignoring `McpError` structure | Poor client diagnostics | Use `McpError::resource_not_found`, etc. |
| Missing `.await` on `server.waiting()` | Server exits immediately | Always await the server handle |
| Implementing `ServerHandler` without capabilities | Client doesn't know what's available | Enable capabilities matching your impl |
| Hard-coding tool schemas | Breaks on changes | Derive `JsonSchema` on argument structs |
